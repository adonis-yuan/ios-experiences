# Tech design: frame structure and message format for a live chat room

This is the wire format behind the
[live room client design](long-connection-client.md): the frames that travel over
the long connection, the message object shown in the room, references, ordering,
reactions, and a draft `.proto`.

## General rules

The format has two layers: a frame is the envelope carried on the long
connection, and a message is what the room actually displays. Encoding is
protobuf, defined independently of the transport, so WebSocket and gRPC can both
carry it as is.

- Rooms are created per event, not per article. Several articles covering the
  same event share one room, so a message that references an article must carry
  its `docid` explicitly.
- Room messages and article comments are stored separately. Referencing a comment
  does not turn the message into a comment.
- Business semantics (acks, reject codes, seq, versions) are all expressed inside
  the payload and never rely on transport mechanisms.
- Every time is a UTC millisecond timestamp generated by the server; the client's
  clock never takes part in any decision.

Id types: the live room's own ids (room, message, poll, client operation ids) are
all UUIDs, sent in protobuf as 16-byte `bytes`; message ids should be UUIDv7.
User ids, `docid` and `comment_id` keep their existing formats.

## Frame types

Every frame carries a version `v` and a `room_id`. A room `seq` is assigned only
when a message is created; edits, deletes and reactions do not consume seq and use
the message's own `ver` to tell old from new.

| Direction | Frame | Purpose | Consumes room seq |
| --- | --- | --- | --- |
| C→S | `hello` | First frame: auth token, protocol version, client version | No |
| S→C | `welcome` | Version negotiation result, heartbeat interval | No |
| C→S | `subscribe` | `room_id` + `latest_n` (default 50), on entering or reconnecting | No |
| S→C | `snapshot` | Reply to subscribe: the latest `latest_n` messages, `head_seq` (current highest seq), private messages, room info `room` (title, state, people here) | No |
| C→S | `send` | `client_msg_id` + `content` + `refs`, sends a message | No |
| S→C | `send_ack` | To the sender: the `msg_id`, `seq` and `server_ts` for a `client_msg_id` | No |
| S→C | `send_reject` | To the sender: `client_msg_id` + reject code (moderation, rate limit, invalid reference) | No |
| S→C | `msg_new` | A new message | Yes |
| S→C | `msg_update` | Changes or deletes an existing message (poll closed, edited, deleted, hidden), carrying the full message and its new `ver` | No |
| C→S | `react` | `client_op_id` + `msg_id` + `emoji` + `op` (`add` / `remove`); Me too uses the fixed key `metoo` | No |
| S→C | `react_ack` / `react_reject` | To the actor: the server timestamp for the `client_op_id`, or a reject code | No |
| S→C | `reaction_delta` | One batch of reaction adds and removes per second; see [Reactions](#reactions) | No |
| C→S | `typing` | Typing indicator, at most once every 3 seconds | No |
| C→S | `vote` | `client_op_id` + `poll_id` + `option_index` | No |
| C→S | `catch_up` | Asks the host for a summary only you can see; the result comes back as `host_new` | No |
| C→S | `mark_read` | Reports the seq read up to before leaving, for list unread counts | No |
| S→C | `stats` | People here, typing, Seen by / reply counts, poll percentages | No; transient, may be dropped |
| S→C | `host_new` | A private message from the host (ONLY YOU) | No; uses the user's own `pseq` |
| S→C | `error` | Connection-level error: auth failed, version too old, room closed | No |
| Both | `ping` / `pong` | Application-level heartbeat | No |
| C→S | `page_sync` | Lists the pages of interest with their known message and reaction versions | No |
| S→C | `page_sync_result` | Current versions of those pages; changed pages get message deltas and reaction deltas or summaries; pages with known version 0 are sent whole (that is, paging) | No |
| C→S | `delete_msg` | Deletes one of your own messages; on success everyone receives `msg_update` (deleted, ver+1), on failure the sender receives `delete_reject` | No |

Endpoints that do not use the long connection (REST):

- Watch for me: `POST` / `DELETE /rooms/{id}/watch`. It is a push subscription,
  unrelated to the connection.
- Full reaction list:
  `GET /messages/{msg_id}/reactions?emoji=E&after_ts=T&limit=100`.

## Message object

`msg_new` carries the full message object; messages sent whole or as deltas by
page_sync use the same structure.

| Field | Type | Set by | Notes |
| --- | --- | --- | --- |
| `msg_id` | bytes (UUID) | Server | Globally unique; the client dedupes on it |
| `room_id` | bytes (UUID) | Server | Room id, which maps to an event, not an article |
| `seq` | uint64 | Server | Contiguous and increasing within the room; assigned at creation and never changed; used for ordering and history paging |
| `ver` | uint64 | Server | Content version, +1 on every edit or delete; the client keeps only the copy with the largest `ver` |
| `server_ts` | int64 (UTC ms) | Server | Display time only |
| `client_msg_id` | bytes (UUID) | Sender | Idempotent resends; echoed only to the sender |
| `sender` | Sender | Server | `kind` (`user` / `host` / `system`), `uid`, `name`, `place`, `avatar` |
| `content` | Content | Sender | `oneof`: `text` / `poll` / `agg`, extensible |
| `content.text.mentions` | Mention[] | Sender | `uid` + `offset` + `length`, in UTF-16 code units |
| `refs` | Ref[] | Sender supplies ids, server fills snapshots | Reference list; see [References](#references-refs) |
| `reactions` | ReactionSummary[] | Server | Per emoji: total, whether I reacted, the first 3 users; see [Reactions](#reactions) |
| `status` | enum | Server | `ok` / `deleted` / `hidden`; a deleted message keeps a placeholder and its seq is not reused |
| `fallback_text` | string | Server | Shown when the client does not recognise the `content` type |

Example (shown as JSON for readability; on the wire it is protobuf):

```json
{
  "msg_id": "m_01JBX...",
  "room_id": "evt_8f3a",
  "seq": 1024,
  "server_ts": 1757865600123,
  "sender": { "kind": "user", "uid": "u_123", "name": "Marcus T.", "place": "Columbus, OH" },
  "content": { "text": { "text": "One outlet isn't a story yet. @Host",
                          "mentions": [{ "uid": "host", "offset": 30, "length": 5 }] } },
  "refs": [],
  "status": "ok",
  "fallback_text": "One outlet isn't a story yet. @Host"
}
```

## References (refs)

Every reference goes into `refs`; the four scenarios are just different
combinations. Each reference is made of `rel`, `target` and `snapshot`.

- **`rel`**: `reply` increments the target's reply count and triggers the
  "Someone replied to you" push; at most 1 per message. `quote` is display only;
  at most 3.
- **`target`**: one of `doc` / `comment` / `room_msg`; the client uploads only the
  id.
- **`snapshot`**: a summary of the referenced content, validated and filled in by
  the server, and displayed by the client as is. The client therefore cannot forge
  referenced content, and does not need a separate request per reference. When the
  referenced content is deleted or hidden, `snapshot.status` is `deleted` or
  `hidden`.
- **Only one level is expanded**: if the referenced message has references of its
  own, the snapshot does not include its `refs`.
- **docid and url**: both are accepted upstream, and the server resolves a url to a
  docid. Downstream always returns the docid; the url appears only in the snapshot,
  for display.

| Scenario | `rel` | `target` |
| --- | --- | --- |
| 1. Comment on an article | `quote` | `doc`: `docid` |
| 2. Reply to an article comment | `reply` | `comment`: `comment_id` + `root_comment_id` + `docid` |
| 3. Plain message | — | `refs` is empty |
| 4. Reply to or quote a room message | `reply` or `quote` | `room_msg`: `msg_id` + `seq` |

Scenario 1, commenting on an article:

```json
"refs": [{
  "rel": "quote",
  "target": { "doc": { "docid": "0zX9aB" } },
  "snapshot": { "status": "ok", "title": "City council approves transit plan...", "source": "Example News", "url": "https://..." }
}]
```

Scenario 2, replying to an article comment. `comment` carries its own `docid`, and
the snapshot brings back both the article and the comment; when replying to a
top-level comment, `root_comment_id` equals `comment_id`:

```json
"refs": [{
  "rel": "reply",
  "target": { "comment": { "comment_id": "c_555", "root_comment_id": "c_500", "docid": "0zX9aB" } },
  "snapshot": { "status": "ok", "author": "Ray B.", "text": "Anyone seen a second outlet...",
                "doc": { "title": "City council approves transit plan...", "source": "Example News" } }
}]
```

Scenario 3, a plain message:

```json
"refs": []
```

Scenario 4, replying to a room message:

```json
"refs": [{
  "rel": "reply",
  "target": { "room_msg": { "msg_id": "m_01JBW...", "seq": 1011 } },
  "snapshot": { "status": "ok", "author": "Marcus T.", "text": "One outlet and one author..." }
}]
```

If room messages ever need to be written through as article comments, add a
separate `crosspost { docid, comment_id }` field to express that identity rather
than reusing `refs`.

## Ordering, entering and loading history

On entering, the user sees the latest messages, not the place they left off;
earlier messages are paged in by seq range as the user scrolls up.

1. **Order by `seq`**, never by timestamp. Server nodes have clock skew between
   them, and several messages can share the same millisecond. `server_ts` is for
   display only.
2. **Seq assignment**: the server assigns seq when the message is persisted. Each
   room has a single writer, starting at 1 and increasing contiguously. Messages
   rejected by moderation get no seq; deleted messages keep a placeholder and their
   seq is not reused. Private messages use the user's own `pseq`, plus an
   `anchor_seq` saying which room message they appear after. When merging, room
   messages compare as (seq, 0, 0) and private messages as (anchor_seq, 1, pseq).
3. **Entering and reconnecting both fetch the latest**: the client sends
   `subscribe(latest_n = 50)` and the server replies with `snapshot`: at least the
   50 latest messages (starting point aligned to a multiple of 100, so 50–149 are
   actually returned and the first scroll-up is a fully aligned page) and
   `head_seq`. The protocol offers no "resume from the seq you left at".
4. **History paging**: the client sends `page_sync` with the page to fetch
   ([S−100, S) or [S, S+100)) at known version 0. In `page_sync_result` the server
   returns every message in the page (`PageMessages.full = true`, ascending,
   including delete placeholders) and the page's reaction summaries
   (`PageReactions`). Because seq is contiguous with no gaps, a page is exactly 100
   messages. S must be a multiple of 100 so every client's pages line up and the
   server can share a cache keyed on (room, page, version). Later changes to pages
   already cached come as `page_sync` deltas too.
5. **Gaps**: the `snapshot` and locally cached messages may not be contiguous. The
   client only records the range, and fetches it per rule 4 when the user scrolls
   there; it does not fill it proactively.
6. **Seq gaps on the long connection**: a `msg_new.seq` above the local maximum
   plus 1 means a push was lost. If 100 or fewer were skipped, fill the page with
   page_sync; otherwise treat it as a gap.
7. **Edits and deletes**: `msg_update` carries the full message and its `ver`. The
   client keeps only the copy with the largest `ver`, and messages returned by
   page_sync overwrite the local cache by `ver` in the same way.
8. **Dedupe**: by `msg_id`; the same message may arrive through `snapshot`,
   `msg_new` / `msg_update` and page_sync.
9. **Messages being sent**: show them optimistically at the bottom under their
   `client_msg_id`. On `send_ack`, fill in the `seq` and re-sort. If your own
   `msg_new` arrives before the ack, merge the two by `client_msg_id`.
10. **High-frequency counters go through `stats`**: Seen by, reply counts, people
    here and poll percentages are pushed at most once per second per room, with a
    `ver` field; the client keeps only the latest.

## Reactions

A message's reactions are a map: emoji → a list of (user, timestamp), earliest
first. A hot message can have thousands of people on one emoji, so the message
carries only a summary and the full list is paged in on demand.

- **The summary in the message, `ReactionSummary`**: `emoji`, `count`, `me`
  (whether I reacted), `earliest` (the first 3 users with timestamps).
- **Full list**: `GET /messages/{msg_id}/reactions?emoji=E&after_ts=T&limit=100`,
  returned earliest first.
- **Add and remove**: the client sends `react(op = add / remove)`, applies it
  locally first, and rolls back on `react_reject`. The server assigns the
  timestamp.
- **Idempotency**: at most one record per user, message and emoji. A duplicate add,
  or removing a record that does not exist, both count as success. Adding again
  after removing gets a new timestamp and goes to the end.
- **The `reaction_delta` push**: one batch per room per second, each item being
  `msg_id`, `emoji`, `uid`, `ts`, `op`. For the same (msg_id, emoji, uid) the item
  with the larger `ts` wins, so out-of-order arrival still gives the right result.
- **No seq**: reactions are not part of the room's operation sequence; both the
  entry snapshot and paging page_sync carry the latest summaries.

Page version sync (over the long connection): for each page ([S, S+100)) the
server keeps two versions, `mver` (incremented when a message in the page is
deleted, hidden, edited or added) and `rver` (set to the current `rseq` whenever a
reaction in the page changes). `snapshot` carries `page_versions` for the pages it
contains. The client sends `page_sync` listing the pages of interest and their
known versions; the server answers with `page_sync_result`, giving each page's
current versions and, for pages whose `rver` moved, the latest reaction summaries
for the whole page. For pages whose `mver` moved, it sends the messages changed
since the known version (PageMessages) rather than the whole page; a page not
cached locally uses known version 0 and is sent whole. The server keeps no client
state and caches results by (room, page, version). While online, `msg_update`
carries the page's new versions in the frame (`ServerFrame.page`) and
`reaction_delta` carries `rseq`; while these arrive contiguously the client updates
its known versions directly. On a gap or after reconnecting, it sends one
`page_sync` for the loaded pages.

The client's in-memory structures and their complexity are covered in the
[client design](long-connection-client.md#review-decisions).

## Forward compatibility and limits

New capabilities only add fields or `oneof` branches, and old clients must
degrade safely.

- Protobuf field numbers are only ever added, never changed; removed fields are
  held with `reserved`.
- An unknown `content` type shows `fallback_text`; an unknown reference type shows
  "unsupported reference".
- An unknown frame type is ignored; the connection stays open.
- `hello` carries the protocol version; when the server no longer supports it, it
  returns `error` and the client prompts an upgrade.

| Limit | Maximum |
| --- | --- |
| Text length | 500 characters (pending product confirmation) |
| `reply` references per message | 1 |
| `quote` references per message | 3 |
| Snapshot expansion depth | 1 level |
| Entry `latest_n` | Default 50, the minimum returned; aligning the start to a multiple of 100 means 50–149 are actually returned |
| History paging `limit` | 100 |
| `ReactionSummary.earliest` | 3 users |
| Distinct emoji per message | 20 (pending product confirmation) |
| `stats` / `reaction_delta` push rate | Once per second per room |

## Draft proto definition

Below is a proto3 draft of the structures above. Field names and numbers are to
be frozen after server review.

```proto
syntax = "proto3";
package liveroom.v1;

// Ids of live room objects (room, message, poll, client ops) are 16-byte UUIDs.
// User ids, docid and comment_id keep their existing string formats.

// ---------- Frames ----------
message ClientFrame {
  uint32 v = 1;
  oneof body {
    Hello hello = 10;
    Subscribe subscribe = 11;
    Send send = 12;
    Ping ping = 13;
    React react = 14;
    Typing typing = 15;
    Vote vote = 16;
    CatchUp catch_up = 17;
    MarkRead mark_read = 18;
    PageSync page_sync = 19;
    DeleteMsg delete_msg = 20;
  }
}

message ServerFrame {
  uint32 v = 1;
  bytes room_id = 2;
  PageVersion page = 3;  // set on msg_update: that page's new versions
  oneof body {
    Welcome welcome = 10;
    SendAck send_ack = 11;
    SendReject send_reject = 12;
    Message msg_new = 13;
    Message msg_update = 14;
    Snapshot snapshot = 15;
    Stats stats = 16;
    HostMessage host_new = 17;
    Error error = 18;
    Pong pong = 19;
    ReactAck react_ack = 20;
    ReactReject react_reject = 21;
    ReactionDelta reaction_delta = 22;
    PageSyncResult page_sync_result = 23;
    VoteReject vote_reject = 24;
    DeleteReject delete_reject = 25;
  }
}

message Hello { string token = 1; uint32 protocol_version = 2; string client_version = 3; string platform = 4; }
message Welcome { uint32 protocol_version = 1; uint32 heartbeat_sec = 2; }
message Subscribe { bytes room_id = 1; uint32 latest_n = 2; uint64 known_pseq = 3; }  // snapshot returns host messages after known_pseq
message Snapshot {
  repeated Message messages = 1;
  uint64 head_seq = 2;
  repeated HostMessage host_messages = 3;
  RoomInfo room = 4;
  uint64 reaction_rseq = 5;
  repeated PageVersion page_versions = 6;  // message and reaction versions of each page in this snapshot
  repeated Sender senders = 7;  // latest profiles of the senders above
}
message Send { bytes room_id = 1; bytes client_msg_id = 2; Content content = 3; repeated RefInput refs = 4; }
message SendAck { bytes client_msg_id = 1; bytes msg_id = 2; uint64 seq = 3; int64 server_ts = 4; }
message SendReject { bytes client_msg_id = 1; RejectCode code = 2; string reason = 3; }
message Ping { int64 client_ts = 1; }
message Pong { int64 client_ts = 1; int64 server_ts = 2; }
message Error { ErrorCode code = 1; string reason = 2; uint32 retry_after_sec = 3; }  // 0 = client backoff decides

enum RejectCode { REJECT_UNSPECIFIED = 0; MODERATION = 1; RATE_LIMITED = 2; INVALID_REF = 3; TOO_LONG = 4; ROOM_CLOSED = 5; MUTED = 6; POLL_CLOSED = 7; }
enum ErrorCode { ERROR_UNSPECIFIED = 0; UNAUTHENTICATED = 1; VERSION_UNSUPPORTED = 2; ROOM_NOT_FOUND = 3; OVERLOADED = 4; KICKED = 5; }

// ---------- Room ----------
enum RoomState { STATE_UNSPECIFIED = 0; LIVE = 1; WARM = 2; CLOSED = 3; }
message RoomInfo {
  bytes room_id = 1;
  string title = 2;
  RoomState state = 3;
  uint32 here_count = 4;
  int64 closed_at = 5;  // 0 = still open
}

// ---------- Message ----------
message Message {
  bytes msg_id = 1;          // UUIDv7 recommended
  bytes room_id = 2;
  uint64 seq = 3;            // assigned once at creation, never reused
  int64 server_ts = 4;       // UTC ms, display only
  bytes client_msg_id = 5;   // echoed to the sender only
  Sender sender = 6;
  Content content = 7;
  repeated Ref refs = 8;
  MessageStatus status = 9;
  string fallback_text = 10;
  uint64 ver = 11;           // +1 on every edit or delete
  repeated ReactionSummary reactions = 12;
  string label = 13;         // host tag, e.g. PINNED / UPDATE / LAST 10 MIN
}

message HostMessage { Message message = 1; uint64 pseq = 2; uint64 anchor_seq = 3; }

message Sender {
  enum Kind { KIND_UNSPECIFIED = 0; USER = 1; HOST = 2; SYSTEM = 3; }
  Kind kind = 1; string uid = 2; string name = 3; string place = 4; string avatar = 5;
  uint64 profile_ver = 6;  // larger wins when merging cached profiles
}

enum MessageStatus { STATUS_UNSPECIFIED = 0; OK = 1; DELETED = 2; HIDDEN = 3; }

message Content {
  oneof kind { Text text = 1; Poll poll = 2; Aggregate agg = 3; }
}
message Text { string text = 1; repeated Mention mentions = 2; }
message Mention { string uid = 1; uint32 offset = 2; uint32 length = 3; }  // UTF-16 code units
message Poll { bytes poll_id = 1; string question = 2; repeated string options = 3; bool closed = 4; int32 my_choice = 5; }  // -1 = not voted
message Aggregate { string text = 1; }

// ---------- Refs ----------
enum RefRel { REL_UNSPECIFIED = 0; REPLY = 1; QUOTE = 2; }

message RefTarget {
  oneof target { DocTarget doc = 1; CommentTarget comment = 2; RoomMsgTarget room_msg = 3; }
}
message DocTarget { string docid = 1; string url = 2; }  // url accepted upstream only
message CommentTarget { string comment_id = 1; string root_comment_id = 2; string docid = 3; }
message RoomMsgTarget { bytes msg_id = 1; uint64 seq = 2; }

message RefInput { RefRel rel = 1; RefTarget target = 2; }
message Ref { RefRel rel = 1; RefTarget target = 2; RefSnapshot snapshot = 3; }

message RefSnapshot {
  MessageStatus status = 1;
  string author = 2;
  string text = 3;
  DocSnapshot doc = 4;
}
message DocSnapshot { string title = 1; string source = 2; string url = 3; }

// ---------- Reactions ----------
enum ReactOp { OP_UNSPECIFIED = 0; ADD = 1; REMOVE = 2; }

message React { bytes client_op_id = 1; bytes msg_id = 2; string emoji = 3; ReactOp op = 4; }
message ReactAck { bytes client_op_id = 1; int64 ts = 2; }
message ReactReject { bytes client_op_id = 1; RejectCode code = 2; }

// ---------- Other client ops ----------
message Typing { bytes room_id = 1; }
message Vote { bytes client_op_id = 1; bytes poll_id = 2; uint32 option_index = 3; }  // a rejection comes back as VoteReject
message VoteReject { bytes client_op_id = 1; RejectCode code = 2; }
message CatchUp { bytes room_id = 1; }
message DeleteMsg { bytes client_op_id = 1; bytes msg_id = 2; }  // success comes back as msg_update
message DeleteReject { bytes client_op_id = 1; RejectCode code = 2; }
message MarkRead { bytes room_id = 1; uint64 read_seq = 2; }
message PageVersion { uint64 page_start = 1; uint64 mver = 2; uint64 rver = 3; }  // page = [page_start, page_start + 100)
message PageSync { bytes room_id = 1; repeated PageVersion known = 2; }
message MsgReactions { bytes msg_id = 1; repeated ReactionSummary reactions = 2; uint32 replies = 3; }
message PageReactions { uint64 page_start = 1; uint64 rver = 2; repeated MsgReactions messages = 3;  // full summaries, set when ops cannot be served
  repeated ReactionDelta.Item ops = 4;  // changes since the client's known rver, when retained
}
message PageSyncResult {
  uint64 rseq = 1;
  repeated PageVersion versions = 3;  // current versions of every requested page
  repeated PageReactions changed = 2;  // unchanged pages omitted
  repeated PageMessages messages = 4;  // pages whose mver moved; unchanged pages omitted
}
message PageMessages {
  uint64 page_start = 1;
  uint64 mver = 2;
  repeated Message changed = 3;  // changed since the known mver, reactions unset
  bool full = 4;  // true = whole page: known mver was 0 or is past retention
}

message Reactor { string uid = 1; string name = 2; string avatar = 3; int64 ts = 4; }
message ReactionSummary {
  string emoji = 1;
  uint32 count = 2;
  bool me = 3;
  repeated Reactor earliest = 4;  // oldest first, at most 3
}

message ReactionDelta {
  message Item { bytes msg_id = 1; string emoji = 2; string uid = 3; int64 ts = 4; ReactOp op = 5; }
  repeated Item items = 1;  // same (msg_id, emoji, uid): larger ts wins
  uint64 rseq = 2;          // per room, +1 per batch; a gap means deltas were lost
}

// ---------- Stats ----------
message Stats {
  uint64 ver = 1;
  uint32 here_count = 2;
  uint32 typing_count = 3;
  map<string, MsgCounters> msg_counters = 4;  // key = msg_id as UUID string
  map<string, PollTally> poll_tallies = 5;    // key = poll_id as UUID string
  RoomState state = 6;
}
message MsgCounters { uint32 seen = 1; uint32 replies = 2; }
message PollTally { repeated uint32 votes = 1; uint32 total = 2; }
```
